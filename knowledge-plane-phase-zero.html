Knowledge Plane, Phase Zero

A remote knowledge service that gives Inflexa its method choices as cited, versioned rules and tested script templates. The model fills typed parameters. The service does the deterministic work. Phase 0 proves it on bulk RNA-seq with three new tools, one plan-step field, and no other change to Inflexa.

Summary

Build the knowledge plane as one small remote service with a typed, deterministic API. The service holds three kinds of knowledge object: a rule (a situation-to-method claim with conditions, strength, and cited evidence), a method (a statistical procedure with its packages and versions), and a template (a tested script with a typed parameter contract and pinned environment). The client sends a structured description of the analysis situation. The service matches the rules, assembles the procedure, renders the template, and returns claim identifiers, evidence, and a snapshot digest. The client model never writes a query and never writes a method from memory. For a standard step it does not write the script either. It emits slot values, and the tool writes the rendered script into the workspace.

Inflexa reaches the service through three tools: knowledge_recommend, knowledge_check, and knowledge_template. Phase 0 adds these tools and one field: a grounding object on the plan step that holds the claim identifiers, the snapshot digest, the template, and a one-line reason. The step agent also writes a decision record into its output tree, which the signed provenance already hashes. Phase 1 adds the validation gate and the provenance event. Phase 2 adds the offline snapshot and the next modalities. The open-source CLI runs without the service by default. The tools attach only when a license configures the service, and a plan validates as today without them.

The knowledge lives as code in a private repository: one YAML file per claim, validated by a LinkML schema, reviewed in pull requests, released as a dated snapshot with a content digest. Phase 0 serves the snapshot from a single SQLite file inside one container. A graph store is a later decision, not a Phase 0 requirement, because the Phase 0 corpus is about fifty rules and ten templates.

Goal 1 · Smaller models
87.6vs 88.6

BFCL v4 single-call accuracy of Qwen3-8B against Claude Opus 4.5. Small models call one typed tool as well as frontier models, and fail on chains. Thus the service does the hops [17].

Goal 2 · Grounded chain
0DOIs today

The skill packs carry no DOI and no PMID. The plan step has no rationale field. Each served claim carries a content-hashed identifier and at least one resolvable source [Sec. 3].

Goal 3 · Less time
44–57%

The band in which all 23 models on FlowBench select the right tool when they must infer it. Explicit tool selection reaches near 100%. A named method removes a retry loop [27].

Goal 4 · Fewer tokens
slots, not scripts

Output tokens cost several times input tokens. The model emits slot values, and the tool writes the script from the template. Phase 0 measures output tokens per step against the from-scratch baseline [Sec. 10].

What changed since the last draft

The 2026-08-26 draft set the direction: typed tools, nanopublication-shaped claims, a mandatory planner brief, and a grounded plan gate. This proposal keeps that direction and changes six things, because the deep research and the constraint on Phase 0 give different evidence.

  • Phase 0 changes no prompt and no seam. It adds three tools and one plan-step field. The three tools carry their own contract in their descriptions. The grounding rides in the new field and in a step deliverable. The brief and the gate move to Phase 1.
  • The store follows the corpus, not the ontology. The last draft chose Oxigraph first. About fifty rules do not justify a triple store. Phase 0 compiles the knowledge repository into one SQLite file. The LinkML schema can emit RDF and SHACL when a graph query is necessary, thus the path to Oxigraph stays open [50, 63].
  • One check call, not a critic loop. LLM-Modulo evidence is real, but a ten-iteration loop conflicts with the time and token goals, and small models collapse on chains [11, 12, 17, 18]. The service does the loop work inside one call and returns one procedure.
  • Procedures, not facts. Skills work as procedural anchors (65.7% of the mechanism), not as knowledge injection (4.5%) [33]. Each answer is an ordered procedure with a template, and the references hang off the steps.
  • The rule copies are two, not three. The full decision tree lives in the skill pack and in the sandbox prompt. The planner prompt holds one statistics rule only. A partial third copy sits in the shared omics pack [Sec. 3].
  • The evaluation is a non-inferiority test with a noise floor. Paired agent evaluations show a noise floor near 15 points, and 18.5% of benchmark verdicts disagree with experts [69, 70]. Phase 0 pre-registers a margin, uses fresh simulated data, and keeps airway and pasilla for template tests only.
  • Scripts are reused, not rewritten (added 2026-09-04). The template tool writes the rendered script and the decision record into the step workspace through the existing mutator seam. The model emits slot values only, and a residual change goes through edit_file as a small diff. Output tokens fall, and the same template gives the same script across runs and across analyses.

The always-loaded prose, measured

The token goal needs a baseline. The sandbox standards prompt holds 3,755 words and the planner prompt 2,525 words. The bulk transcriptomics agent body holds 535 words, and its skill pack 942 words. The skill loads on demand through a keyword scan. Thus a knowledge tool cannot save tokens by the removal of prose alone. It can save tokens when a named method removes a wrong-method retry, and when a rendered template removes a debug loop. Phase 0 must measure this, not assume it.

The largest output-token item of a step is the script that the agent writes from scratch. A DESeq2 step script of about a hundred lines is on the order of a thousand output tokens or more, and each rewrite in a debug loop pays it again. Output tokens cost several times input tokens. Thus the lever for goal 4 is the script, not the prose. The template tool writes the script, and the model emits slot values. This estimate is a measurement item of Phase 0.

The principles

P1. The client fills typed parameters. It never writes a query.

Each tool takes a flat object with enumerated values. The service runs a tested query and a deterministic rule match. There is no Cypher, SPARQL, or SQL from the model on either side.

Why. Frontier models reach about 60% execution accuracy on CypherBench, and 8B models 19%, with silent errors [7]. A deterministic semantic layer reached 98 to 100% where text-to-SQL with the same 2026 models reached 84 to 90%, and it fails in the open instead of in silence [9]. Small models match frontier models on a single typed call [17, 19].

P2. One call returns one procedure. The service does the hops.

A planning question gets one answer: an ordered procedure with methods, parameters, template ids, rules, flags, and evidence. The service joins situation to rule to method to template to source inside the call.

Why. No open model clears 60% on conditional or multi-source tool tiers, and BFCL multi-turn scores fall to 22 to 48% for 4B to 32B models [17, 18]. Every extra step grows context, and context growth is a measured cause of failure [20, 22]. In-service joins removed most intermediate tokens in Anthropic's measurements [24].

P3. Return procedures with the evidence attached, not facts alone.

The unit of an answer is a step with a method, a parameter set with sources, and a template. The claims and their DOIs hang off the steps. A concise answer stays under a few thousand tokens. Alternatives and full evidence come on request.

Why. Skills act as procedural anchors in 65.7% of the observed mechanism and as knowledge injection in 4.5% [33]. Expert prose alone gave 1.9 points on ScienceAgentBench and lowered valid execution [29]. Long tool results cut accuracy by 7 to 91% [21]. Prompt bloat cut completion by 28% [31].

P4. A standard step adapts a tested template. It is not free code.

The template carries the imports, the call signatures, the version pins, and the defaults with their sources. The model fills only the slots marked adaptable, as a small JSON object. The service renders the script, and the tool writes it into the step workspace. The model never emits the script. A residual change is an edit_file diff, not a rewrite. The sandbox runs the script and feeds back one error.

Why. Open models reference a non-existent package in 21.7% of generations [35]. Version-conditioned code sits near 50% for frontier models, and execution feedback adds 10 to 24 points [36]. A small model with retrieval decides what to do but cannot write the code for a medium pipeline [28]. Bioconductor changes its API twice a year, thus a pinned template removes a whole failure class [40]. Output tokens cost several times input tokens, and a rendered template keeps the code constant across runs, where free generation gave a run-to-run overlap of Jaccard 0.43 [31].

P5. Every answer is a versioned, cited, content-addressed record.

A claim has a content-hash identifier, an evidence line with direction and type, at least one resolvable source, a strength, and a supersedes link. A snapshot has a date and a digest. A plan records both. The service returns only references that exist in its store.

Why. GO requires an evidence code and a reference on every annotation [51]. Nanopublications and trusty URIs are the mature shape for an immutable claim [48, 49]. Fabricated citations reached about 147,000 in 2025 alone [26]. Citation existence is not support, thus the record carries the supporting span and the evaluation checks it [26, 27].

Determinism where it makes sense. The rule match, the procedure assembly, the template render, the environment check, and the snapshot digest are deterministic. The same situation against the same digest gives byte-identical output.

The model glues. The model extracts the situation from the data profile and the request, selects between two defensible options when the service marks a rule as disputed, fills adaptable slots such as column names and contrasts, and summarizes for the report.

The architecture

Two systems, one boundary. Inflexa stays open source and host-agnostic. The knowledge service stays closed and remote. The tools are the only contract between them, and the snapshot digest is the only shared identifier.

The Inflexa side

One module, harness/src/tools/knowledge/, exports createKnowledgeTools(deps). The deps are the base URL, the API key, the injectable fetch, the farm-lock reader that list_available_packages already uses, and, for the template tool, the workspace mutator that write_file and edit_file already share at harness/src/agents/sandbox/shared.ts:256. The module returns the three tools. Each tool has a flat Zod input schema, a describeCall hook, and an apiFetch call with the retry and timeout policy of the other external tools.

The registrations are three lines. The planner list gains knowledge_recommend and knowledge_check. The sandbox allowlist gains knowledge_template, declared by the bulk transcriptomics agent and the enrichment agent. The conversation agent gains knowledge_recommend through the host-tools seam, from the CLI, with no harness change. The CLI config gains a knowledge block beside the embedding block, and the key comes from the environment only.

The tool descriptions carry the contract. They say when to call, what to send, and where to write the result. The planner description says: call knowledge_recommend before you draft a method step, and fill the grounding field of the step with the returned claim identifiers, the snapshot digest, and the template id. The template description says: send the slot values, and the tool writes the rendered script to scripts/ and the decision record to output/decision_record.json; use edit_file for a residual change. No prompt changes in Phase 0. Whether the model calls the tool without a prompt line is a Phase 0 measurement, and the answer decides the Phase 1 brief.

The one field

The plan step gains one object, grounding. It is optional in both step schemas, thus a stored plan and a plan made without the service both load and validate as today. When the service is configured, the Phase 1 gate requires it on each method step. Phase 0 validates the shape only. The briefing renders the field beside the task fields, thus the step agent reads the template id and the claim identifiers from the step, not from prose.

grounding: {
  status:    "grounded" | "ungrounded" | "flagged",
  snapshot:  "sha256:71ac…" | "none",
  claims:    ["R-0031@e7d0", "R-0044@1a9b"],     // returned by knowledge_recommend in this run
  template:  "tpl-deseq2-two-group@1.4.0",       // optional; absent for a step with no template
  reason:    "6 vs 6 unpaired, fixed effects: DESeq2 Wald with apeglm (R-0031)"   // one line
}

An empty field is visible. The evaluation counts a method step without a value as ungrounded. A planner that called the tool and set the answer aside writes status: ungrounded with a reason. A flag case carries status: flagged and the rule that raised it. The touch points are the two step schemas, workflow-state.ts:16 and plan-schemas.ts:16, and the field list of the briefing at briefing.ts:43.

Reuse, not rewrite

Today the step agent writes each script from scratch through write_file, and the whole script is output tokens. With the template tool the model sends a slot object of about a hundred tokens. The tool renders the template, writes scripts/<step>.R and output/decision_record.json through the workspace mutator, and returns the path, the slot report, and the environment match. The write goes through the same seam as write_file, thus the confinement and the provenance event are the ones that exist. The tool runs in workflow execution mode, as the two file tools do at write-file.ts:37.

A change that the slots do not cover goes through the existing edit_file tool as a small search-and-replace diff. The rendered script marks each adaptable region with a comment, thus the diff lands in a known place and the decision record lists it as an unvetted edit. Two effects follow. Output tokens per standard step fall from the size of a script to the size of a slot object plus the diffs. And the code of a step is the same across runs, and across analyses that share a design, because the template and the slots determine it. The evaluation measures both [Sec. 10].

With and without the service

The open-source CLI has no access to the knowledge plane by default. A license enables it. Thus the harness must run as it does today when the service is absent, and the design makes absence the default state, not a failure state.

  • The tools attach only when configured. createKnowledgeTools takes an optional client. With no knowledge block in the CLI config, the factory returns no tools, the planner list and the sandbox allowlist are what they are today, and no description of a knowledge tool enters the context. This is the pattern of the host-tools seam and of the eyes seam: an absent optional member is a normal condition.
  • The field is optional in both schemas. A plan without a grounding value validates as today. The tool description asks the planner to fill it, and the Phase 0 evaluation counts an empty field as ungrounded. The Phase 1 gate requires the field only when the service is configured, in the same way as the resource policy of the planner: absent, validation skips the check.
  • The skill packs stay as the open-source knowledge. With the service absent, the planner and the step agents work from the prose skills, as today. With the service present, the service is authoritative for method choice, and the step agent gets templates instead of snippets.
  • The license is the API key. The CLI config block knowledge: { baseUrl, apiKey } carries it, the key comes from the environment, and a managed deployment configures it always. The harness never knows about licenses. It sees a client or nothing.
  • Configured but unreachable returns the typed unavailable result. The run continues from the skills, and the count is reported. This stays as proposed.

Two products share one knowledge source without drift when the skill decision trees become an output of the knowledge build. The build renders the consensus rules of a modality as the decision-tree section of the skill pack, with the DOIs, and the team commits the rendered section on each release. The open-source pack then carries the same rules as prose, and the service carries the conditions, the evidence, the templates, and the gate. This is a Phase 1 item.

The service side

The service is one stateless container. It loads a snapshot by digest at start, serves the typed API over HTTPS, and exposes the same operations as MCP tools for curation clients and for tests. Phase 0 uses one API key for one tenant. The OAuth 2.1 profile of the MCP specification is the growth path when the service gets a second tenant [15].

  • Typed API. Validates the input against the generated JSON Schema, returns a typed result with match, snapshot, and the answer. A validation failure names the field and the permitted values. Absence returns match: none with the nearest conditions.
  • Normalizer (Phase 1 option). When a later phase adds a constrained free-text field, a model inside the service maps the text to the situation schema and to vocabulary terms. The output is validated and echoed back, thus the client sees what the service understood. No query generation. Phase 0 has no free text and no normalizer.
  • Rule engine. Evaluates each rule condition against the normalized situation. The hit policy is: collect all applicable rules, order by specificity, return both sides of a disputed rule, and raise a flag when a consensus rule forbids the requested analysis. The engine is code over decision tables, not an OWL reasoner, because no ontology can express the conditional rule [43, 56].
  • Procedure assembly. Walks the ordered step types of the modality (QC, filter, normalize, model, test, shrink, enrich, report), attaches the selected method and its parameters with their default_source, and names one template per step.
  • Template renderer. Validates the slot values against the parameter contract of the template, renders a logic-light template in a sandboxed engine, checks the R or Python syntax, and returns the script with a decision record. It compares the farm versions with the template pins and returns exact, compatible, or mismatch. The script marks each adaptable region with a comment, thus a later edit_file diff lands in a known place.
  • Snapshot store. One SQLite file per snapshot: rules, methods, templates, sources, vocabulary mappings, plus an FTS5 index for the free-text path. Read only. Identified by date and content digest.

The provenance path

Phase 0 records the grounding in the plan and in the files. The plan step carries the grounding field in the durable state, and show_plan and inspectRun expose it. The step agent writes the rendered script and the decision record with write_file, and each write becomes an inflexa:FileToolWrite activity with a sha256 hash. Thus a reader of the package can open output/decision_record.json and find the rule ids, the snapshot digest, the template version, and each slot value with its source.

This is reported provenance in the sense of the paper. The tool call itself is observed by the loop, with its input and its outcome, but it is not signed. Phase 1 adds the observed record: a knowledge-consulted session event with the query, the digest, and the returned claim identifiers, and claim entities through appendLifecycleAction. The paper's distinction stays intact: the consultation is observed, the use is reported, and the gate checks the use against the observation.

The query contract

Three tools, one situation schema, and one response envelope. The situation schema is the semantic layer of the service. It ships with definitions of each term, because a 4 KB definition of the conventions raised analytics accuracy by 17 to 23 points for three frontier models, more than any model change did [10].

The situation schema

The fields are flat, enumerated where possible, and never carry sample rows or identifiers. The data profile gives most values. The planner extracts the rest from the request.

Response rules

  • Absence is a typed result. match: none names the nearest applicable conditions and the reason. The planner then proceeds from the skill prose and marks the step ungrounded. Phase 0 counts these.
  • A flag is a result, not an error. A confounded batch, a missing replicate, and a large heterogeneous cohort each return match: flag with the rule and the permitted outcome, for example a descriptive analysis or a stop with a question to the user.
  • A disputed rule returns both sides. The planner selects one and states the choice in the step. The evaluation rubric scores the statement, not the side.
  • A validation failure is an error tool result that names the parameter and the permitted values, thus the model can correct itself in one turn.
  • The service is unreachable. The tool returns match: unavailable after the retry policy. The run continues from the prose skills. Phase 0 records the count. A strict mode is a Phase 2 option.
  • The tool definitions are stable. Their hash is part of the snapshot record, because a changed definition invalidates every prompt-cache level and changes behavior in silence [23].

The knowledge model

One LinkML schema defines the classes. It generates the JSON Schema that validates the curator files, the TypeScript types of the tool contract, and, when a graph is wanted, the OWL and SHACL [50]. The categorical slots bind to external terms through meaning annotations. New concepts get an INFLEXA: term at once, and an SSSOM mapping set connects each local term to an official one when it exists [45, 46].

Today the same rule lives as a sentence in a reference file of the skill pack. In the service it has an identity, conditions that a validator can run, sources that a reviewer can open, a direction on each source, and a version that the plan can pin.

The classes

  • Situation. The schema of Section 6. The rule conditions are predicates over it.
  • Rule. Assertion, conditions, action (a step type, a method, parameter values), strength (consensus, common-practice, disputed), evidence quality and recommendation strength as two axes in the GRADE sense [52], alternatives, disputed sides, evidence lines, status (active, scheduled-for-deprecation, deprecated with replaced-by), supersedes, license, curator, LLM-drafted flag.
  • Evidence line. Direction (supports, disputes, neutral), ECO type, CiTO intent, the source, a paraphrase with a section anchor or a verbatim span of about 25 words, the retrieval date [55, 57].
  • Source. DOI or PMID, title, year, venue, license, version and date for a vignette or a pipeline page. Verified at build time with the Crossref and PubMed resolvers, which the harness already has in harness/src/citations/.
  • Method. Label, STATO term, EDAM operation, packages with bio.tools ids and version ranges per Bioconductor release, the templates that realize it.
  • Template. Six blocks, in the nf-core module shape: identity (id, semantic version, EDAM ids, citations, license), applicability (modality, count source, design patterns, minimum replicates), parameter contract (JSON Schema 2020-12, each slot with adaptable and default_source), inputs and outputs with EDAM formats, environment (Bioconductor release, bioconda pins, image digest, annotation source and release), body, and tests (dry run, golden anchors on airway and pasilla, one test per adaptable enum value) [58, 59, 60].
  • Snapshot. Date, content digest over canonical JSON (RFC 8785), the schema version, the vocabulary version IRIs, the tool-definition hash, the changelog.

Versioning

A published snapshot is never edited. A correction is a new snapshot. A rule is never deleted. It becomes deprecated with a replaced-by link, and the tool response includes the replacement, thus an old plan can be upgraded by machine. This is the OBO Foundry lifecycle, and it is the reason every reused ontology stays readable across years [47]. The API and the schema use semantic versions. The content uses date plus digest.

The curation pipeline

Every production knowledge base in 2025 and 2026 works the same way: a model drafts, a curator signs, and the record keeps the evidence. GO reports 86.7% curator agreement with model drafts and a review time cut from 30 to 5 or 10 minutes per article when the draft carries verbatim quotes [53]. The knowledge plane copies this loop and runs it as code.

  1. Seed. The 54 rules of this research, each with verified primary sources, are the first corpus. The skill decision trees, the nf-core parameter defaults, the Bioconductor workflow articles, and the tool user guides are the next sources, in license order.
  2. Draft. A model writes one YAML file per claim from a source, with the paraphrase or the short quoted span, the section anchor, the conditions, and the proposed strength. The file carries the LLM-drafted flag and the model identifier.
  3. Review. A pull request. A structural reviewer checks the schema, the links, and the tests. A named scientific reviewer checks the assertion and the strength. Nothing unreviewed enters a snapshot.
  4. Gates. CI validates each file against the LinkML JSON Schema, resolves each DOI and PMID, finds each quoted span in its source, runs each template against its golden tests inside the pinned image, and diffs the snapshot against the previous one into the changelog.
  5. Release. A tag, a snapshot file, a digest, a signed manifest. The service pulls it by digest.
  6. Re-verification. Each Bioconductor release (April and October) and each nf-core release re-runs the template tests and re-checks each rule that cites a vignette default. The canonical RNAseq123 workflow was in build error on the Bioconductor 3.23 report of 2026-09-01, and the nf-core DESeq2 module still pins 1.34.0 against 1.52.0 in the current release. Rot is the normal state without a schedule [59].
  7. Evolution. A run feeds the queue. A successful script with an unvetted edit, a flag that an analyst overrode, and a match: none result each become a curation item. A good adapted script becomes a candidate template version, with the same review. Nothing learned enters a snapshot without a curator, because self-generated skills gave no benefit on average [33].

Cost

The one published per-item cost of biocuration is 219 dollars per article at EcoCyc [54]. With model drafts and quotes, the Phase 0 set is about 190 reference checks at 10 minutes each, plus one to two hours per rule for authorship and review. That is 60 to 140 curator hours for the rules, before the templates and their tests. The rules digest of this research already holds the drafts.

Licensing rules for the served snapshot

Decided on 2026-09-04: the path with the fewest legal questions.

  • The Phase 0 vocabularies are attribution-only or public domain: ECO (CC0), STATO (CC BY 3.0), OBI (CC BY 4.0), and the minted INFLEXA terms. EDAM appears only as an optional cross-reference IRI, with none of its label text in the snapshot, because its share-alike clause is the one question the set would otherwise raise.
  • The gene-set collections the rules recommend are CC BY or CC0: MSigDB Hallmark and C5, the Reactome and WikiPathways subsets of C2, and GO. The KEGG legacy sets and KEGG MEDICUS stay out of the snapshot. A user with a KEGG license adds them on their side [71].
  • A source enters the snapshot as metadata and a locator, never as full text. A claim carries a paraphrase and a section anchor by default. A verbatim span is limited to about 25 words, attributed, and used only when the exact wording carries the threshold or the rule. The text and data mining exceptions permit the extraction, not the redistribution [72].
  • Each record carries its license, its source version, and its retrieval date. The attribution duty and the provenance record are the same metadata.

Phase 0, the proof of concept

Scope: bulk RNA-seq differential expression and enrichment, from a count matrix or from Salmon quantifications. Out of scope: read alignment, single-cell, and every other modality. The proof succeeds when a small model with the tools plans as well as the current frontier model without them, on an evaluation that would catch the difference.

The service stack, decided

Decided on 2026-09-04: the service in TypeScript on Bun, with bun:sqlite, one container. Reason: the harness is TypeScript, the tool contract types come from the same LinkML-generated JSON Schema on both sides, and the team lives in one language. The build pipeline runs in Python inside CI, because LinkML, OAK, and the nanopub tooling are Python. The container runs on any small host. Fly.io or Cloudflare Containers cost a few dollars per month, and object storage holds the snapshots [64, 65].

Exit criteria

  1. Knowledge base checks pass. Recall at 1 of at least 0.9 on a gold set of 60 design-to-method queries. Every DOI and PMID resolves. Every template is green on airway and pasilla in the pinned image.
  2. The model calls the tools without a prompt line. The planner calls knowledge_recommend in at least 90% of runs, on both model sizes. If it does not, the Phase 1 brief is necessary and Phase 0 says so.
  3. Non-inferiority holds. The small model with the tools is non-inferior to the frontier model with the prose skills on the rubric, at the pre-registered margin.
  4. The chain is grounded. At least 95% of method steps carry a claim identifier that resolves in the snapshot. Zero fabricated references.
  5. Time and tokens are measured per run, with a breakdown, and reported with confidence intervals. Output tokens per step are reported on their own, against the from-scratch baseline. No target in Phase 0, only the truth.

Effort

About six to eight weeks for one engineer with a scientific reviewer available for the rule review. The service skeleton and the tools take two to three weeks. The curation takes 60 to 140 hours across the same period. The evaluation harness takes one to two weeks, and the runs take days.

The evaluation

The claim "equally correct with a smaller model" is a non-inferiority claim. It needs a pre-specified margin, a paired design, repeated runs, and a validated judge, because agent evaluations carry a noise floor near 15 points and public tool benchmarks disagree with experts on 18.5% of verdicts [69, 70]. Airway and pasilla are in every DESeq2 tutorial, thus they serve the template tests and never the evaluation.

Tasks

Eight design patterns: two-group unpaired at n=3 and at n=6, paired with subject blocking, balanced batch as covariate, a 2×2 genotype-by-treatment interaction, a short time course, a confounded batch (expected outcome: flag), and no replicates (expected outcome: descriptive only). Each pattern has three datasets: two fresh simulations with compcodeR or Polyester with a new seed per campaign, and one held-out GEO dataset with relabeled samples and a reference analysis by two experts [73, 74]. That is 24 tasks. A memorization probe runs first, and any dataset a model reproduces from memory is excluded.

Conditions

A 2×2 factorial: model in {frontier, small open} and knowledge in {prose skills as today, knowledge plane tools}. The prose-skills arm is the open-source product as shipped. Three runs per task and condition, 288 runs per small model. The small model must call tools through a native function-calling API, because prompt-mode tool calling loses most of its accuracy [17]. Ablations on the small model: tools without knowledge_check, and guidance-only responses without templates. An inert comparison, the same condition with two seed sets, reports the empirical noise floor next to every effect.

The target models

Decided on 2026-09-04: GLM 5.3 Flash and Qwen 3.8 27B are the two small targets. Each connects through the direct connection mode of the CLI: an OpenAI-compatible endpoint, an explicit model id, and the per-role model settings, thus the planner and the step agents run the small model while the utility role stays cheap. The family guard of the CLI applies only to an auto-resolved id in proxy mode, thus neither model needs a change there. Before the main runs, a smoke test of 30 cases per model checks three things: native tool calls against the three flat schemas, the abstain behavior on an irrelevant request, and the slot-object fill on five templates. A model that fails the smoke test is reported, not evaluated. Its numbers on the public leaderboards are not a substitute, because those carry an 18.5% disagreement rate with experts [70].

Metrics

  • Primary. A rubric score of 0 to 100 on eight criteria: method fits design, QC present, low-count filter, normalization, model formula and contrasts, FDR and shrinkage, enrichment universe and set choice, report completeness. Two blinded experts score a 40-run calibration set. A frontier judge is accepted only at a weighted kappa of at least 0.7 against them, and 15% of runs stay double-scored.
  • Result accuracy. Recall, precision, and AUROC of DE genes against the simulated truth. Jaccard and Spearman against the expert reference on the GEO tasks. nf-core/differentialabundance 2.0.0 on the same counts is the non-LLM anchor.
  • Grounding. Share of method steps with a resolvable claim identifier. Statement support of each rationale against the returned evidence, RAGAS style, validated on 100 hand-labeled items. Fabricated reference rate, target zero [25].
  • Behavior. Tool-call validity, execution success per step, sandbox retries, run-to-run Jaccard of the DE gene sets, and the outcome on the two flag cases.
  • Consistency. The normalized edit distance between the scripts of a step across runs of the same task, and across tasks that share a design pattern. A template gives a distance near zero. Free generation does not.
  • Efficiency. Input, output, and cache-read tokens per run, price-weighted, with output tokens per step reported on their own; wall-clock; loop iterations; against a measured baseline breakdown of the current CLI.

The margin is 5 rubric points, one-sided at 97.5%. A task-level paired bootstrap handles the repeated runs. Holm correction covers the four primary contrasts. The full design of 48 tasks and five runs with a mixed model is the Phase 1 evaluation, when the rule set is larger.

Phase 1 and Phase 2

0proof

Tools only, bulk RNA-seq

Three tools, one plan-step field, the service, the seed knowledge base, and the evaluation. No prompt, seam, or kernel change. The grounding rides in the field and in the decision record. Exit on the five criteria of Section 9.

1contract

Make the grounding structural

  • The gate on the grounding field: validatePlan rejects a claim identifier that the service did not return in this run, and rejects a method step with status ungrounded when the service was reachable.
  • A knowledge brief in the planner seed, computed host-side from the data profile beside the reference and package censuses, if the Phase 0 call rate says the description alone is not enough.
  • knowledge_check as a stage of fullyValidate, with violations as structured issues into the existing rejection loop. One check per submit attempt, not a loop.
  • A knowledge-consulted session event and claim entities through appendLifecycleAction, and a lineage reader that knows the new relation. The plan becomes a P-Plan entity.
  • Delete the duplicated method prose from the bulk transcriptomics and enrichment prompts. The skill pack stays as the procedure and as the open-source knowledge. The service owns the mutable facts.
  • The knowledge build renders the skill decision tree of each covered modality from the consensus rules, with DOIs, thus the open-source pack and the service carry one rule set.
  • A constrained free-text field with the server-side normalizer, only if the Phase 0 fill quality of the small models is poor.
  • The synthesis attaches the claim evidence to the report through the existing citation resolver verdicts.
2growth

Offline, more modalities, the graph when needed

  • A KnowledgeBase seam with three realizations: the remote client, an embedded snapshot, and none. The snapshot ships as a signed, digest-addressed artifact that an air-gapped install pulls once.
  • Single-cell, proteomics, and the next modalities, one seed sprint each, with the same schema.
  • Oxigraph or another store behind the same typed API when a multi-hop question appears, for example a path from a design through a method to every benchmark that ranked it [62].
  • The OAuth 2.1 profile of MCP for a second tenant, and a strict mode that stops a run when the service is unreachable.
  • A fine-tuned server-side querier for free-text questions, if the normalizer ablation shows demand [8].

Risks

  • The model ignores the tool. Without a prompt line, a small model may skip an optional call. Phase 0 measures the call rate as an exit criterion, and the Phase 1 brief is the remedy. The tool description is written as onboarding text, with one example, because examples raised complex-parameter accuracy from 72 to 90% [16]. The grounding field makes an omission visible: the evaluation counts an empty field as ungrounded.
  • Tokens move the wrong way. Tool definitions and responses can exceed the small skill prose. The gain must come from fewer iterations and retries. The evaluation reports the breakdown, and the definitions stay small and first in the request so the cache holds [23].
  • Over-determinism. A disputed practice encoded as one action gives confident wrong plans on edge cases. Disputed rules return both sides, flag cases return a flag, and each override by an analyst becomes a curation item.
  • Version drift. A template validated on one DESeq2 version runs on another in the farm. The template tool sends the farm versions and records the environment match in the decision record. A mismatch warns in Phase 0 and can block in Phase 2.
  • Injection through served content. KB text is partly model-drafted and partly quoted. The tool result is data, never an instruction. Claims are declarative sentences by curation rule. The tool-definition hash is pinned per snapshot, because tool poisoning is the most common MCP client failure and a changed definition is a silent behavior change [66, 67].
  • Personal data. The situation schema carries counts and categories, never sample rows, and Phase 0 has no free-text field. The query log of the service is still a record of each user's research program, and it needs a retention policy before a second tenant.
  • Curation bottleneck. The value is the hand-checked rule layer, and it decays on each Bioconductor release. The schedule in Section 8 and a named scientific reviewer are the mitigation.
  • Template rigidity. A template that does not cover a design forces free code or a poor fit. The escape hatches are the extra_args slot and the edit_file diff, both listed as unvetted in the decision record, and each such case is a curation item for the next template version.
  • Two sources of truth. The prose skills stay, because the open-source CLI runs on them by default, and they can drift from the service. With the service configured, the service is authoritative for method choice. Phase 1 makes the skill decision tree an output of the knowledge build, thus the two carry one rule set, and removes the duplicated prompt prose.
  • Evaluation validity. Tutorial datasets are memorized, judges drift, and the noise floor is wide. Fresh simulations, held-out GEO sets with relabeled samples, a calibrated judge, and a pre-registered margin are the mitigation.

Decisions for you

These six changed the work. All six are decided, on 2026-09-03 and 2026-09-04, and the sections above carry the consequences.

  1. The service language. Decided: TypeScript on Bun with a Python build pipeline, as Section 9 describes.
  2. The Phase 0 grounding home. Decided: one additive grounding field on the plan step, optional in both schemas, as Section 5 describes. The decision record file stays as the signed copy.
  3. The target small models. Decided: GLM 5.3 Flash and Qwen 3.8 27B, through the direct connection mode of the CLI, gated by the smoke test of Section 10.
  4. Operation without the service. Decided: the open-source CLI has no access by default, and a license enables it. Absent means no tools attached and no field required, and the run works from the skills as today. Configured but unreachable means the typed unavailable result and a run that continues from the skills. Section 5 gives the mechanism.
  5. Licensing. Decided: the path with the fewest legal questions. Attribution-only vocabularies, EDAM as cross-reference IRIs only, no KEGG in the snapshot, paraphrase with a section anchor, and verbatim spans under 25 words. Section 8 gives the rules.
  6. Data minimization. Decided: typed fields only in Phase 0, no free text, no normalizer. A constrained free-text field with the normalizer is a Phase 1 option, taken only if the fill quality of the small models is poor.
