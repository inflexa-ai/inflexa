## 1. Shared download utility

- [x] 1.1 Extract a generic HTTPS→file utility (`src/lib/download.ts`: `downloadToFile` + `declaredContentLength`) — HTTPS re-checked on the post-redirect URL, sha256, `.part`→atomic activation, progress events, injected `fetch`. Unit-tested (`download.test.ts`).
- [x] 1.2 `refs/store.ts`'s `downloadArtifact` is now a thin wrapper over `downloadToFile`, keeping only what is genuinely the installer's: the `assertOwnedPath` ownership check (the generic utility has no notion of an installer-owned tree, and this is what stops a symlinked ancestor redirecting a write outside the store) and the dataset/path attribution the generic progress events cannot carry. The private `declaredContentLength` is deleted in favour of the exported one, the inline `FetchLike` spellings in this file are replaced with the shared type, and the duplicated transfer body — stale-part discard, https-on-redirect, byte counter, `pipeline`, `stat`, `sha256File` — is gone along with its `createWriteStream`/`Transform`/`Readable`/`pipeline` imports. `lib/download.ts` now reports an unreachable host as `http_failed` rather than `io_failed`, which both fixes a misclassification (its own doc calls `io_failed` a local fs fault) and makes the installer's remap faithful: every wire fault becomes `download_failed`, only a local fs fault stays `io_failed`, so all three existing error-type assertions hold unchanged. The download cache entry is dropped as soon as it is staged rather than after activation — it is a second full copy of the artifact and nothing resumes from it — and the install test now asserts the WHOLE cache directory is empty afterwards, not just that no `*.part` remains, which is the assertion that actually catches a leak. 94 refs tests green.

## 5. Adjacent defects this change surfaced

- [x] 5.1 `--analysis` was silently swallowed on every subcommand that declares it: the root program declares the same option names (`index.ts:93`), so commander binds the value to the ROOT and the subcommand's action receives `{}` — the flag reached no handler, on six commands, since `864d25a`. `registerAction` now installs a `preAction` hook that hydrates each action command with the ancestor-parsed values it lacks, fixing all of them at one choke point. NOT `enablePositionalOptions()`: that was tried and reverted before, because it turns a root-style flag placed after a subcommand (`inflexa sessions --project x`) into a hard "unknown option" — pinned by a regression test, which is what caught the second attempt. Both halves of the trade-off are now pinned in `cli.test.ts`.
- [x] 5.2 `--max-size <size>` overrides the per-Series ceiling (`500MB`, `64GB`, or a plain byte count; binary units, so a size copied out of the command's own output round-trips). The over-cap message names the flag and the size that would allow it.
- [x] 5.3 The `run_inflexa` subprocess bound is now QUIET time, not wall-clock: `idleTimeoutMs` (120 s, rearmed on every chunk either stream produces) plus a 30-minute absolute backstop. A flat deadline cannot tell a working command from a wedged one, so any value was wrong for someone — 2 minutes killed a legitimate multi-gigabyte download, and a value generous enough to spare it would have let a hung command hold the turn just as long. `geo download` feeds it a `file_progress` heartbeat every 5 s during a transfer, which doubles as the readout a long download needed anyway.
- [x] 5.4 The harness `search_geo_datasets` description no longer claims fetching is impossible. It still forbids planning an in-sandbox download (the sandbox genuinely has no egress) but defers the question of whether the data can be obtained at all to the agent's actual tool set — it names no host command, since the harness is host-agnostic and `skills`/prompt content must not encode one host's inventory.
- [x] 5.5 `--project` is gone from `geo download`: a project scopes to a SET of analyses and `resolveContext` answers a project ref with a picker, never a single analysis, so the flag could only ever have failed. `--analysis` names a target.
- [x] 5.6 An unresolvable `--analysis <ref>` now reports that no analysis matches the ref (with the known analyses), instead of telling a user who just passed `--analysis` to pass `--analysis`. The other half of that ternary was dead: `resolveContext` only answers `pick` for an unmatched ref or a `--project`, and this command declares no `--project`, so the "more than one could match" arm could never print.
- [x] 5.7 The artifact transfer was the one GEO request that took its first answer. Listings and size probes route through `fetchGeo`'s retry; the transfer called `downloadToFile` directly, which does a single un-retried fetch — so one shed 403/503 mid-Series aborted the set and the staging teardown discarded every artifact already transferred. That also left this change's own requirement ("the command lists **or fetches** … retries with backoff") half-implemented. `downloadToFile` now takes an opt-in retry schedule, defaulted off so the reference-data caller is behaviourally unchanged, and the shedding predicate is shared with `fetchGeo`. Pinned by a test that fails on the old code.
- [x] 5.8 The pre-transfer size sweep was unbudgeted and silent — one HEAD per artifact, each free to spend ~3.5 s retrying a shed 403, with no progress event until it finished. For a Series of many small files that is minutes of silence before a byte moves, inside a subprocess whose agent-side bound IS silence (5.3), so the sweep could get the child killed for a step whose worst honest outcome is "size unknown". It now runs behind a queue of 4 under one 15 s deadline covering the whole sweep, mirroring `measureReferenceDownload` against the same host. See D12 for why the listings and the transfers stay serial.
- [x] 5.9 `runCli` captured child output through pipes, which empties out under full-suite load: the child ran and exited correctly, but `stdout`/`stderr` arrived as `""`, so every assertion about what a command PRINTED failed while its exit-code assertion passed. It now redirects the child's streams to files and reads them back — a file has no capacity limit to hit and no reader to schedule. This fixes three pre-existing failures (`project new` ×2, `repair` ×1).
- [x] 5.10 `spawnInflexa` armed its two deadline timers before `Bun.spawn`, which throws on a launch fault (ENOENT on the binary) and propagates out of the function — leaving both pending with nothing to clear them. Not merely a stray `expire()` into an abort nobody reads: a pending `setTimeout` holds the event loop, so the process stays alive for the whole bound (measured: a 4 s bound kept a would-be-immediate exit open for 4004 ms; in production that is up to 30 minutes). Fixed by arming them after the spawn instead of wrapping it — a `try/catch` that clears and rethrows produces no `Result` and is the shape this subsystem's error-handling rule calls a smell, while the ordering removes the class outright. Untested by design: the only observable is process exit latency, since Bun's `getActiveResourcesInfo()` does not report timer handles (verified — it returns `[]` with the leak present), and a wall-clock subprocess assertion would join the flaky family in 6.2 for a fault with no other coverage.
