# Design

## Context

harness is the second subsystem of the epic #611 that moves to oxlint. The typed programs were fixed first (#605, commit `89387da4`): `tsconfig.json` includes all of `src` with `"types": ["bun", "node"]`, the build reads `tsconfig.build.json`, and `tsconfig.eslint.json` is gone. prov-kernel moved second (#606) and is the reference: `oxlint.config.ts` default-exporting `typescript({ env: { node: true } })`, `typecheck.config.ts` with the `must-use-result` `consumers` option, `lint` = `bun --bun oxlint`, `typecheck` = `inflexa-typecheck`, tests in the `test/` folder of their directory, and a Claude hook that walks up to the nearest `oxlint.config.ts`. The local research `tmp/claude/lint/harness.md` holds the inventory: the rule map with counts, the directives, and each document that names ESLint. The inventory was taken with plugin 0.3.0 on the 2026-09-28 tree; this change pins the same 0.7.0 line as prov-kernel, so the research is a map, each count in it (and each count copied from it into these artifacts) is research-era, and the pinned 0.7.0 run on the branch-start tree is the authoritative report list.

ESLint leaves nothing behind that oxlint and the type check command do not cover. The one typed rule outside oxlint's reach, `neverthrow/must-use-result`, runs in `inflexa-typecheck` on the same program, with the consumer list of the patched wrapper (`unwrapOrThrow`, `passGate`, `deliverNotice`, `keepSuspendingRefusal`) as its `consumers` option and `_unsafeUnwrapErr` as a handled method natively. The patched wrapper, its bun patch, and the ESLint stack that hosted them go away.

## Goals / Non-Goals

**Goals:**

- harness lints with the full `typescript()` preset of `@inflexa-ai/oxlint-plugin` 0.7.0 at the exact versions prov-kernel pins, and typechecks with `inflexa-typecheck`; no ESLint dependency, config, patch, or directive remains.
- The move and the turn-on land as one state: the final `oxlint.config.ts` turns off no preset rule except `typescript/await-thenable` and `typescript/no-confusing-void-expression` in the test files.
- `bun run lint`, `bun run typecheck`, `bun run test:full`, `bun run build`, `bun run smoke`, and `bun run lint:python` pass in harness; the cli typecheck passes against the linked working-copy harness.
- The emitted `.js` bytes of `dist/` change only where a report asks for a code change; each sweep that claims to be type-level proves itself against the recorded pre-change hash list, and only the `.d.ts` files change through the interface-to-type sweep.

**Non-Goals:**

- No lint change in cli (epic steps #610, #608) and no change to the prov-kernel configuration.
- No release, no publish, no version bump of `@inflexa-ai/harness`; the `.d.ts` surface change is recorded and the release workflow owns the bump.
- No `noUncheckedIndexedAccess` (decision 6), no new pre-commit hook (the #611 decision stands: CI and the Claude hook run lint), and no `directive-guard` command in the harness scripts.

## Decisions

1. **Versions and scripts follow prov-kernel exactly.** `oxlint@1.85.0`, `oxlint-tsgolint@7.0.2003`, `@inflexa-ai/oxlint-plugin@0.7.0`, `@inflexa-ai/typecheck@0.7.0`, and `@typescript/native: npm:typescript@7.0.2` in devDependencies; `typescript` stays `^6.0.3`, the line that builds `dist/`. `lint` = `bun --bun oxlint` (the TypeScript config loads under Bun, so the runner Node version never loads it); `typecheck` = `inflexa-typecheck` (the command runs under its Node shebang, because its TypeScript 7 dependency reaches Node `child_process` internals that Bun's spawn lacks). Alternative rejected: running the command under `bun --bun` — it crashes, verified on this machine during #606.

2. **`oxlint.config.ts` keeps the prov-kernel shape with the harness additions.** `typescript({ env: { node: true }, restrictedImports: [...], instanceofErrorAllowIn: [...] })` plus override blocks: `typescript/no-unused-vars` with the four `^_` options and `typescript/switch-exhaustiveness-check` with `considerDefaultExhaustiveForUnions: true` on `**/*.{ts,tsx,js,mjs}` (the prov-kernel glob, so the JavaScript scripts keep the `^_` escape); `no-console` on `src/**`; the `no-console` exemption for `src/lib/console-logger.ts` and its test at both the pre-move path `src/lib/console-logger.test.ts` and the post-move path `src/lib/test/console-logger.test.ts` (the block names both from the start, and the stale entry goes when the move lands); the `className` ban for `**/*.tsx` in a block that repeats the full `restrictedSyntax()` list plus the `JSXAttribute[name.name='className']` entry, because an override replaces the options of `eslint-js/no-restricted-syntax` and nothing can subtract one entry; the vendored `js/recommended` set on `scripts/**/*.mjs` (the pinned plugin applies `eslintRecommended` to `**/*.{ts,tsx}` only, and exports no named copy); and the two bun-types rules off for the test-file globs. The `restrictedImports` entry bans `@inflexa-ai/tsprov` and `@inflexa-ai/tsprov/*` with the message the ESLint config carried. The config sits in `harness/` so the `src/**` globs resolve relative to it.

3. **`typecheck.config.ts` sets the four consumers.** `must-use-result` runs as `['error', { consumers: ['unwrapOrThrow', 'passGate', 'deliverNotice', 'keepSuspendingRefusal'] }]` for `src/**`. This is the same consumer list the patched ESLint wrapper knew (`eslint.config.js` `RESULT_CONSUMERS`), now typed and on the same program, so the done-when of #609 holds: the command gives the same reports the patched rule gave — none on the current tree, with the four rewritten directives still suppressing their sites. The `_unsafeUnwrapErr` twin that the wrapper taught the plugin is handled by the rule itself.

4. **`scripts/**/*.ts` enter `tsconfig.json`.** `include` becomes `["src", "scripts/**/*.ts"]`. The typed rules and the type check command then see the scripts with the real types; today no tsconfig includes them, so tsgolint types them with default options and the strict typed rules read the `error` type. The build is unaffected: `tsconfig.build.json` carries its own `include`. Alternative rejected: excluding the scripts from the typed rules — it leaves them permanently untyped and hides real reports.

5. **The six directives take their new forms, and the one sanctioned site escape is the plugin's own.** The two `no-control-regex` directives in `src/input-sanitization.ts` become `// oxlint-disable-next-line no-control-regex -- <the reason they already carry>`. The four `must-use-result` directives in the result and hooks tests become `// typecheck-disable-next-line must-use-result -- <reason>`, the form the type check command reads; a directive without a reason is itself a problem. Each report of the preset is fixed in code. For `eslint-js/no-restricted-syntax` alone, a site that no replacement fits carries the plugin's own `// oxlint-disable-next-line eslint-js/no-restricted-syntax -- <reason>` form. A factory `syntax` lift (for example `syntax: { regex: false }`) turns a preset ban off for the whole package: it counts as a turned-off rule under the done-when of #607, it is not an implementor decision, and it needs the coordinator's sign-off with the reason that no replacement exists for that ban class anywhere in the code — the prov-kernel precedent (`JSON.parse` round-trips of PROV-JSON) is the shape of such a sign-off, not a volume escape. Never a bare disable, never a disable without a reason, never a fifth override block.

6. **`noUncheckedIndexedAccess` stays off.** The issue asks for the decision first because `typescript/no-non-null-assertion` (1902 reports) and `typescript/no-unnecessary-type-assertion` (1253) read the same `!` differently when the flag is on. With the flag off — the state of both harness and the prov-kernel reference — an index access has the element type, so a `!` on it is unnecessary, both rules agree that it goes, and removing it cannot change the types. A `!` on a genuinely nullable value is a real guard site and gets a real check. Turning the flag on would re-type every index access of the harness and balloon the change into a type-correctness sweep that no issue of the epic asks for. Alternative rejected: `noUncheckedIndexedAccess: true` — a tsconfig semantics change outside the scope of both issues, with no probe behind it.

7. **Each test moves into the `test/` folder of its directory.** `test-placement` reports a file whose parent directory is not `test`, and it matches by filename pattern alone — the setup rig and the fixture runners hold test files too (`src/__tests__/setup/dbos.test.ts`, `src/__tests__/setup/require-reaper.test.ts`, `src/tools/lib/__fixtures__/fixture-runner.test.ts`, `src/loop/__fixtures__/scripted-provider.test.ts`), and they move into the `test/` folder of their own directories like every other test. The fix is `src/lib/result.test.ts` → `src/lib/test/result.test.ts` and the same one level down for each test file (330 on the current tree; the research-era count said 299), the integration tests included. The non-test helpers of the rig (`postgres.ts`, `dbos.ts`, `require-reaper.ts`, ...) and the fixture data stay where they are: the rule matches test files, not helpers or data. Each relative import gains its `../` or `test/` segment, and each path that reads a fixture through `import.meta.url` or `import.meta.dir` is re-based. `tsconfig.build.json` adds `src/**/test` to its excludes beside the existing patterns, so a shared helper that lands in a `test/` folder cannot leak into `dist/`. The plain `*.test.ts(x)` exclusion patterns stay as they are.

8. **The interface-to-type sweep is the recorded API break.** `no-interface` flags each `interface` declaration; the fix is a `type` alias with the same members, which keeps every literal, extension, and implements clause working and removes declaration merging. About 825 of the 862 declarations ship in `dist/*.d.ts`; an embedder that merged a declaration into a harness interface stops compiling. The break is recorded in the proposal, the cli jobs link the working-copy harness in every CI run (so the in-repo consumer proves the surface), and the release workflow owns the version bump. No `interface` is kept through a per-site escape.

9. **The report clusters are fixed rule by rule, in passes that a script can repeat.** The move lands first with the reporting rules still off in the working tree, so the tool change is verifiable on its own; each pass then turns one cluster on, fixes its reports in code, and keeps the config clean behind it; the last pass deletes each temporary `off` entry, and the final `git diff` of the config holds only the settings of decision 2 and 3. The largest clusters and their fix shapes: `no-non-null-assertion` and `no-unnecessary-type-assertion` (remove the `!` and the redundant cast; guard the genuinely nullable site), `require-assertion-safety` (a `SAFETY:` comment per cast that states the invariant), `no-unsafe-type-assertion` (narrow the source type or parse with a schema), `require-await` (drop `async` from a double that awaits nothing), `no-restricted-syntax` (regex 497: a parser, a zod schema, or a builtin that knows the grammar; `JSON.parse` 62: a schema parse; timers 44: a wait that ends on an `AbortSignal`), `no-conditional-spread` (build the object without conditional keys, tsprov-style, with the golden tests proving the bytes), and the smaller rules one by one (`no-base-to-string`, `no-unnecessary-condition`, `no-double-cast`, `no-typeof-object`, `no-unknown-type-guards`, `restrict-template-expressions`, `unbound-method`, `explicit-function-return-type` outside the tests, `export-at-declaration`, `no-empty-schema`, `no-implied-eval` in the page-script tests, the `no-unsafe-*` leftovers that the scripts-in-tsconfig decision surfaces, `no-deprecated` at its true sites). A report that no code shape satisfies goes to the coordinator with its evidence, not to a silent disable.

10. **`no-instanceof-error` lifts through the factory's own option.** `instanceofErrorAllowIn` lists the error helpers that turn a thrown value into an `Error` — the research points at `lib/result.ts` and `lib/logger.ts`; the pinned run gives the exact list, and each entry carries the reason in the config comment. The same class of factory-native lift as the `syntax` option: never an override block, never an inline disable.

11. **CI keeps the job name and pins its Node.** `lint (harness)` keeps its name, because `release-harness.yml:88` and `release.yml:70` wait for it. The ESLint step becomes the oxlint step (`bun run lint`), the typecheck step runs `bun run typecheck` (the command prints the `tsc --noEmit` diagnostics and the rule reports in one run), and the job gains `actions/setup-node` at the pinned version with Node 24, the same pin the prov-kernel job and the release workflows use, because the command needs Node 22.18 or later. The root Claude hook needs no edit: it walks up from the edited file to the nearest `oxlint.config.ts`, so harness joins it the moment the config exists.

## Risks / Trade-offs

- [The interface-to-type sweep breaks an embedder that declaration-merges] → recorded as **BREAKING** in the proposal; the cli typecheck against the linked harness proves the in-repo consumer; the release notes own the rest.
- [A cluster fix changes runtime behavior through a rewritten expression] → `bun run test:full` runs after each pass; the golden fixtures and the smoke run prove the bytes and the boot path; the emitted `.js` hashes are compared before and after the sweeps that claim to be type-level only.
- [The bun-types exemption masks a real void-return bug in a test] → the exemption is scoped to the two rules and the test globs only, and the type check command still typechecks the tests.
- [The pinned 0.7.0 run reports sites the 0.3.0 research does not map] → the pinned run is the authoritative list; the research counts are the map, and a site with no clear fix goes to the coordinator with its evidence.
- [`bun install --frozen-lockfile` fails in CI on a stale lock] → the lock is regenerated with the platform binaries of `oxlint` and `oxlint-tsgolint` (linux-x64 for CI, darwin-arm64 locally) and the frozen install is the verification.
- [The cli linking steps disturb the harness install] → the harness acceptance runs before `harness:local` / `kernel:local` in cli, and any link side effect is undone with a fresh `bun install --frozen-lockfile` in the touched subsystem, the caution #606 recorded.
- [TypeScript 7 of the type check command reports diagnostics TypeScript 6 misses] → each diagnostic is a real type correction fixed at its site, the same discipline #605 applied.

## Migration Plan

The change lands as one branch. Rollback is reverting the branch: no data, no wire bytes, and no published artifact move with it. The version bump and the npm publish stay with the release workflow. The intermediate `off` entries of the staged passes never leave the working tree, so the branch tip carries only the final configuration.
